## Most consequential remaining issue

**P1 integration gap, retained legacy behavior — ReaderFileManager.swift:245–249 and :624–708.** Drive preparation is generation-fenced, but metadata scans are not. A refresh in progress captures `[localDrive, cloudDrive]` before awaits, so it can continue scanning A after initialization B replaces the tuple. B's unstructured non-force refresh joins A (:628–634) without requesting followup. If no task is active, the two-second debounce (:636–641) can suppress B's scan entirely. A can later assign `self.files` (:673) and soft-delete Realm rows absent from its discovered URLs (:685–697) while B is the installed tuple. The scan task checks its own cancellation, but never validates `initializationID` or a drive/storage generation. Parent cancellation after preparation does not cancel this independent `Task`.

Concrete schedule: A scan suspends in old drive directory discovery → B prepares and installs drives → B schedules non-force refresh that joins A → A resumes and publishes A inventory/tombstones → no B followup requested. MainActor serializes each synchronous segment; it does not prevent this interleaving across suspension. The orphan write uses RealmBackgroundActor and explicitly refreshes metadata in its transaction, so stale inventory can become durable synced deletion rather than just stale UI.

**Current port does not newly introduce this scan architecture.** During review, the first observed draft awaited `refreshAllFilesMetadata()` then validated initialization, which would have falsely acknowledged B's own inventory. Parent revised it to retain legacy background refresh with an explicit preparation-only comment. That revision removes the new completion claim and is the reviewed final source. Do not say initialization completion establishes generation-matched inventory, cancellation of all work, or safe tombstone reconciliation.

Future fix requires an inventory/storage generation captured with drives/configuration, admission checks before per-file mutation and final publication/orphan transaction, and a queued successor scan that cannot be lost by join/debounce. Simply passing `force: true` requests followup but does not prevent A's stale durable effects before that followup. Do not cancel another caller's shared producer merely because one waiter cancels.

## ReaderFileManager initialization port/tests

No concrete new MainActor/API compile defect found by inspection. `CloudDriveFactory` and `LocalDriveFactory` explicitly carry `@MainActor @Sendable`; `initialize`, token validation and injected test class are MainActor-isolated. The default-root closure is Sendable. The class itself remains nonisolated `@unchecked Sendable`; existing public mutable drive/identifier properties are not made actor-safe by introducing an actor-isolated token, but no broad concurrency refactor is implied by this focused change.

The current prepare-then-publish code preserves the old tuple through cloud/local suspension and ordinary local failure, consumes cancellation after a cloud provider converts it to ordinary failure, and permanently rejects an older attempt after a failed newer attempt. Both drive observers are assigned before the synchronous MainActor tuple publication. The identifier didSet is suppressed during the tuple change, preventing its own redundant refresh task. Cloud construction is intentionally optional; local construction failure now propagates to the caller, whose current SwiftUI host uses `try?`.

Current tests exercise four preparation rejection paths and use a deterministic actor gate, not source matching. They do **not** test a successful nonnil replacement tuple, local-factory suspension/cancellation, synchronous availability-notification reentry, or any successful scan/followup/debounce/orphan schedule. The test named preservation of installed identifier sets only a string with nil old drives, so it does not independently prove existing CloudDrive instances/observers survive failure, although the production assignment order supports that bounded claim. Add successful-tuple and inventory-generation runtime tests when implementing the broader scan contract. Tests not run by request.

## LakeKit progress hide port/tests

No concrete new cancellation or MainActor defect found. `updateProgress` cancels any old hide before publishing successor progress. `LocationBarProgressHide.run` is MainActor, checks cancellation before sleeping and after even a noncooperative successful sleep, then executes synchronous MainActor completion without another suspension. `onDisappear` cancels the pending hide. Therefore an actor-interleaved successor update cancels A before A's final check; if A already completes its synchronous mutation, the successor update occurs afterward and installs B's values. The current helper test explicitly suspends noncooperative sleep and proves cancellation cannot hide/reset B, plus pre-cancel, throwing sleep and normal completion.

Tests operate on the helper rather than a mounted LocationBarProgressBar. Disappearance/appearance and actual SwiftUI State lifetime remain unexecuted. No regression test was added to the Reader root's explicit test-source list, as the LakeKit owned porting doc already records. UInt64 delay conversion retains the pre-existing public hideDelay domain (invalid/negative/nonfinite delays can trap); it is not a newly introduced port defect.
